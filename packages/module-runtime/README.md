# Module runtime

The runtime resolves installed module metadata before evaluating any module code. It accepts only the eight published module IDs from `@scriptorium/contracts`; work data can choose among installed IDs but cannot supply package names or entry points. `resolveModulePlan` validates module and contract versions, dependencies, cycles, and required capabilities without importing packages.

`ModuleRuntime` receives metadata and lazy `createModule(context)` loaders from the selected profile. An absent module reports `redeployment_required` when enabled. An installed module stays unimported while disabled. `activate()` imports enabled module code and exposes its action, UI, and HTTP descriptors; capability factories run only when a module explicitly acquires a required or self-provided capability. A loaded definition must register every capability in its manifest. Optional capabilities are availability-gated: resolving a profile does not enable their provider, and acquisition reports `optional_capability_unavailable` if the provider is absent or disabled. Disabling a provider while required consumers depend on it, or optional consumers hold its lease, is rejected. Module disable aborts calls, cancels jobs, releases capability leases, disposes worker services and calls `dispose()`; the in-process call drain is bounded by `moduleDrainTimeoutMs` (30 seconds by default). A timeout is returned as `module_drain_timeout` after cleanup proceeds. Module disable does not touch module-owned author data.

Action contexts expose the current project and immutable reader, plus `invoke()`/`listActions()` for the shared namespaced action registry and `linkedReader()` for host-registered repositories owned by the same account. Core actions are supplied by the host in `ActionHostContext.actions`; the runtime verifies snapshot identity and effect rules, limits nested dispatch depth, and never provides an author-approval or write port. HTTP contributions are validated when the module activates, but `httpContributions()` returns descriptors without handlers. The API registers those descriptors and calls `invokeHttp()` with its access context; public read handlers cannot propose changes or call more privileged actions. A handler that finishes after its request or module is cancelled cannot return a response. Streamed responses remain part of the module's active-call drain until the body closes, errors, or is cancelled.

One-shot jobs run in a supervised Node child process over Node's dedicated IPC channel and exit after their result. A capability provider can create a reusable `WorkerService` for its own declared worker entry; that process starts on the first lease, serves bounded requests for every consumer, and exits when the last lease is released. `WorkerService.request(request, signal)` requires the calling consumer's abort signal, so disabling a consumer cancels its provider-owned request without killing a worker still used by another consumer. Cancelling a service job aborts that request; a worker that does not drain within the grace period is terminated. Workers receive JSON-bounded job requests (8 MiB maximum input and output) and a minimal environment containing only allowlisted `PATH`, temporary-directory, locale, timezone, and native-library variables. Git and provider credentials, `HOME`, and `NODE_OPTIONS` are not inherited. Worker logs belong on stderr. The supervisor enforces request deadlines (15 minutes by default), validates module/model/snapshot identity and output size, and waits for child processes to exit or close after cancellation, release, or spawn failure. Default admission bounds are CPU-derived one-shot concurrency (capped at 8) with 8 queued jobs, at most 8 persistent services, and one active plus 4 queued jobs per service; hosts may configure these finite limits and `workerExecPath` with `WorkerSupervisorOptions`. Saturation returns the machine error `worker_overloaded`; a worker that cannot spawn returns `worker_start_failed` and releases its slot.

The `ModuleContext` capability pool pins one provider version per capability ID and shares one value across consumers. Capability providers should keep configuration-sensitive model routing in their bounded worker request metadata; the worker must distinguish incompatible model configurations rather than silently reusing one allocation. The profile generator reads pure `scriptoriumModule` package metadata, follows the selected modules' required dependency closure, and emits lazy server and browser loaders only for that closure. `--verify-deploy` checks the actual deployed package tree and its built imports. Core profile generation therefore produces empty optional-module loader maps and does not import or statically reference module packages.

## Worker entry

Compiled worker entry points may use `installWorkerHandler`:

```ts
installWorkerHandler(async (request, signal) => {
  return runBoundedAnalysis(request.input, signal);
});
```

The helper accepts one `job` IPC message, passes an `AbortSignal` to the handler, and returns one machine-readable result or error over IPC. A cancellation message aborts the handler; the supervisor then terminates the process if it does not drain within the configured grace period.
