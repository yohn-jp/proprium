# P0 Canon — `proprium.narrative` (Work Structure and Writing Continuity)

**Status: normative recovery target.** This is the first official authoring plugin to become useful. It interprets one selected Git repository as a work when the existing YAML hierarchy is present, provides volume/chapter/scene navigation and structural editing, and returns the author to the correct manuscript. It does not make a novel schema mandatory for Proprium Core. A repository without this plugin, or without the recognized hierarchy, remains an ordinary Git workspace.

P0 is the first usable authoring slice, not restoration of the complete writing product. Knowledge, Research, Paired Writing and Diagnostics remain P1 requirements; Speaker, Semantic and advanced Publishing remain P2. A plugin package existing, a successful build, or a selectable scene without a real Host editor does not satisfy P0.

## Product role and ownership

Narrative owns the interpretation and guarded editing of the work hierarchy: volume, chapter, scene, their stable IDs, parent links, display titles, order, and the scene-to-manuscript path. It also owns scene reading-mark annotations in the existing scene metadata. It returns typed navigation targets and annotation ranges for the Host's existing editor/reader. The Host owns the generic Git workspace and the existing CodeMirror editor, body Draft, Japanese IME and undo state, ruby/Aozora and vertical reading controls, typography, 400-character-sheet count, scratch, browser recovery journal, local Git checkpoint, ChangeSet review/apply, commit, remote publication, screen layout, rendered annotation controls, focus and navigation guard.

Narrative does not own Bible entities or semantic scene fields (`goal`, `conflict`, `date`, `pov`, `location`, `appears`, `mentions`, `relations`, tags, or other story facts); Knowledge owns those fields and their references. Reading marks are positional annotations, not story facts. Narrative does not own search indexes, assistant/model context, general manuscript/consistency diagnostics, speaker attribution, EPUB or Git. It owns hierarchy and reading-mark diagnostics. It has no network, LLM, database, server, credentials, DOM, or direct browser storage dependency. It works from pinned local repository reads while offline.

The version-one format has one work hierarchy per repository branch. Its logical work identity is the Host's immutable repository identity; the branch and snapshot remain separate request scope. There is no new root `work.yaml`, project UUID, or second work registry. The Host may display a repository label, while Narrative uses the first volume only as a fallback display label. A fork is a different repository identity unless the user explicitly binds it through a separate product contract.

## Data contract

### Git-authoritative source

The existing work layout remains the canonical format:

```text
plot/volumes/<volume-id>/volume.yaml
plot/volumes/<volume-id>/chapters/<chapter-id>/chapter.yaml
plot/volumes/<volume-id>/chapters/<chapter-id>/scenes/<scene-id>.yaml
manuscript/<existing-relative-path>.md
```

Read existing `.yaml` and `.yml` metadata. New metadata uses `.yaml`. New records have the following minimum semantic shape; unknown existing keys remain legal and untouched:

```yaml
# volume.yaml
id: vol-example
type: volume
title: Example volume
order: 1
```

```yaml
# chapter.yaml
id: ch-example
type: chapter
title: Example chapter
volume: vol-example
order: 1
```

```yaml
# scene.yaml
id: sc-example
type: scene
title: Example scene
volume: vol-example
chapter: ch-example
order: 1
manuscript: manuscript/a-different-existing-path.md
```

The optional scene metadata field `readingMarks` is the only Narrative-owned annotation array. A valid entry is `{id:string,offset:integer,length:integer,snippet:string,comment?:string,createdAt:string}`: `id` is nonempty and unique in the scene; `offset` is zero-based UTF-16 code units from the beginning of the linked Markdown body; `length` is a positive UTF-16 code-unit count; `snippet` is the exact body slice `[offset, offset+length)` captured when marked; `comment` is optional and at most 200 UTF-16 code units; `createdAt` is an RFC 3339 UTC timestamp. New marks must match the current saved-body slice and current metadata/body revisions at proposal time. A mark is current only while the current body has the exact same `snippet` at its recorded offset. If text edits make that comparison fail, expose the annotation as stale and do not shift, fuzzy-match, or silently re-anchor it. The Host reader may jump only to a current mark; it gives a stale-mark message otherwise. Invalid array values and invalid rows remain in the original YAML as opaque source; reads report path/index diagnostics instead of dropping them. Updates append/remove only valid targeted entries and preserve all unknown keys inside valid or invalid rows, comments, quoting, order, and formatting. If safe source-level editing is not possible, the proposal fails without rewriting the mark array.

`name` is accepted as a legacy display-title fallback when `title` is absent. A missing `type` may be inferred from the recognized path for read compatibility; a present type that conflicts with that path is a diagnostic. `id` in the document is authoritative; a filename or directory name is not used as a substitute ID. Existing IDs and explicit manuscript links need not match their containing path pattern. New IDs are limited to 1–128 ASCII characters so they remain valid bounded path components.

Repository ID, branch, snapshot, file path, volume/chapter/scene IDs and the legacy Scriptorium `projectId` are distinct. IDs are unique within the current work scope. Existing duplicate IDs are surfaced as ambiguous with every file path; Narrative never chooses one. Explicit new IDs are accepted only if 1–128 ASCII characters match `[A-Za-z0-9_-]+`; collisions reject rather than silently rewriting an explicit ID. Without an explicit ID, the Host form derives the type prefix (`vol-`, `ch-`, `sc-`) plus the NFKC lowercase ASCII slug of the title (non-ASCII/non-alphanumeric runs become `-`, trim edge hyphens, maximum 48 slug characters). A nonempty slug collision appends `-2`, `-3`, and so on. An empty slug allocates `<prefix>1`, then `<prefix>2`, `<prefix>3`, etc. The selected ID is shown before proposal submission.

For display, finite integer `order` values sort ascending; equal values sort by metadata path then ID and produce a warning. Missing or invalid order values remain accessible after ordered siblings, sorted by path then ID, with a warning. A user-approved reorder writes consecutive 1-based integer orders to the complete sibling set. Opening a work never normalizes old order values.

The scene's `manuscript` field is the only authoritative body path. It must be a normalized, repository-relative, Host-authorized path without traversal, URL, or symlink escape. Narrative must never construct a path from `sceneId` when this field exists. A missing/invalid field prevents editor navigation and gives an actionable hierarchy error. A missing body file is reported separately; it is not silently created or replaced during open.

The Host reads and edits manuscript bytes. Markdown frontmatter, ruby/Aozora notation, line endings, author annotations and unrelated body content remain intact under the existing editor contract. Narrative reads only the path and revision for navigation; it does not load a complete manuscript corpus for tree display.

### Revisions, proposals and derived state

Every invocation uses the H0 v2 `ActionRequest`: the Host supplies `request_id`, plugin/action/schema IDs, `Scope`, `Snapshot`, deadline, caller and activation epoch; it also supplies `idempotency_key` for proposals. A guest cannot choose or override repository scope, snapshot, caller or activation epoch. Host `FileRevision` is SHA-256 of exact file bytes (`null` means absent); each metadata row returns its metadata file revision. `scene.open` and `scene.context` resolve the linked manuscript revision for that selected scene only; tree browsing does not read manuscript bodies or require per-scene body reads. The hierarchy revision is an opaque guest-derived revision over relevant hierarchy file revisions and list membership, scoped to this exact Host snapshot. Cursors bind snapshot, parent and tree revision; a stale cursor is rejected instead of mixing trees. A bound GitHub repository's `work_id` is `github:<repository_id>`; an unbound local repository's `work_id` is `workspace:<workspace_id>`. Branch stays in `Scope`, and neither value is persisted as a new work file.

All structure changes are H0 v2 `ChangeSet`s with complete `read_set`, dependency-closed `units`, exact create/replace bytes or sealed byte artifacts, a Host-owned preview and affected paths. The Host request's `idempotency_key` is required for every `propose` action; it is not an action-specific field. Scene creation proposes the new scene YAML and new Markdown file in one inseparable unit; if inserting at a position it also includes every changed sibling revision and order update in that same unit. A reorder includes the complete sibling set in one unit. A path collision, missing parent, duplicate ID or changed tree rejects the complete proposal. A proposal action returns only the Host-owned `proposal_id` and preview; generated IDs, target paths and all bytes are visible in that preview. The Host applies reviewed units with the single writer and returns per-operation receipts and resulting snapshot. No plugin directly writes a file, edits the worktree, commits, publishes, approves, or deletes a proposal.

The guest derives `ChangeSet.id` as `narrative-cs-` plus lowercase hex SHA-256 of canonical JSON `[workspace_id,generation,action_id,idempotency_key]`; the Host's idempotency ledger remains scoped to workspace+plugin+action+key and canonical request digest. Unit IDs and operation IDs append `/unit/<1-based-index>` and `/op/<1-based-index>` to that change-set ID in source operation order. Replaying the same workspace/plugin/action/idempotency key and canonical input digest returns the original proposal or receipt. Reusing that key with different input returns `idempotency_conflict`. A retry after an unknown Host response first queries the existing proposal/receipt; it never creates a second semantic change automatically. Reads are repeatable at their pinned snapshot. Cancellation before proposal submission produces no proposal; cancellation after the Host has accepted a proposal leaves its status for Host reconciliation.

No Narrative-owned Git file is required for P0; the optional portable resume extension below introduces only its explicitly approved marker file. Existing `meta/scriptorium/modules/story/**` is legacy state; preserve it byte-for-byte and do not treat it as a Proprium authority. Layout, current-scene location, editor position and scratch Draft are Host browser state. Host stores a `WritingResume.v1` record separately from Draft text: `{author_scope,workspace_id,repository_id,branch,scene_id,manuscript_path,metadata_revision,manuscript_revision,draft_generation,sentence_index,scroll_top}`. Its storage key includes author, workspace, repo binding and branch. `sentence_index` is null or 1-based positive integer; `scroll_top` is finite and nonnegative. Cursor restoration uses the saved/recovered text only after the Host resolves the exact document and reconciles its journal; Narrative never stores prose or a second Draft. Host maps the sentence index using the Scriptorium Japanese position rules (newline-aware `Intl.Segmenter("ja", {granularity:"sentence"})`, merge Japanese corner-quoted dialogue, 1-based positions and UTF-16 offsets), with the same behavior tested for dialogue, surrogate pairs, CRLF and blank lines. Parsed trees and indexes are disposable `workspace.derived.cache` entries scoped by repository, branch, snapshot, tree revision and parser version. A cache miss, corruption or eviction causes a bounded rebuild, never a source rewrite.

When updating an existing metadata record, preserve every unknown key and value, comments, quoting, ordering, whitespace and line endings outside the targeted fields. Use syntax-aware source edits or a verified round-trip editor. If a requested update cannot retain unsupported syntax, fail with an actionable diagnostic and leave the proposal unsubmitted. A parse-and-`YAML.stringify` rewrite of a full file is not conforming. Reorder touches only each sibling's `order` node; it must not reserialize unrelated fields.

## Public action contract

Public IDs below are stable, typed plugin actions. The Host supplies the H0 v2 `ActionRequest` scope/snapshot/envelope described in [Host/Plugin Contract](../HOST-PLUGIN-CONTRACT.md); those fields are never guest-controlled input. Schemas reject unknown keys and invalid enum values. Read values appear under the common `ActionResult.value` with the exact observed `snapshot`; `Diagnostic` is `{code,path?,message,severity:"warning"|"error"}`. Successful proposal values are only `{proposal_id,preview}`; proposal IDs and previews are Host-owned. `preview` exposes exact affected paths, changed values/bytes, unit boundaries and dependencies before any apply. Read actions and proposal actions use the same typed dispatch through the Host author UI and `plugin_call`; proposals return review references only and approval remains Host-owned. Action descriptors allow `ui,mcp,plugin` callers for public read/propose capabilities, except the explicitly UI-only gesture-bound portable-position action below. `changes.compile` is plugin-callable only by the registered Paired Writing caller and is never an approval path. `scene.open` and `scene.continue` return intents/candidates but never navigate for MCP or plugin callers; only the Host UI may act on them after the normal user gesture, IME and dirty-Draft checks.

Shared schema aliases used below are exact: `NullableString = string|null`; `StructureKind = "volume"|"chapter"|"scene"`; `WorkStatus = "recognized"|"unrecognized"|"malformed"`; `WorkHealth = "clean"|"partial"`; `Diagnostic = {code:string,path?:string,message:string,severity:"warning"|"error"}`; `TreeItem = {id:string,kind:StructureKind,title:string,order?:integer,parent_id:NullableString,metadata_path:string,metadata_revision:string,manuscript_path?:string}`. `ResumePosition = {scene_id:string,manuscript_path:string,metadata_revision:string,manuscript_revision:string,draft_generation:string|null,sentence_index:integer|null,scroll_top:number}` with `sentence_index` positive when present and `scroll_top` finite/nonnegative. `ResumeCandidate` has the same fields except it adds current `title` and uses current revisions. `HostChangePreview = {title:string,read_paths:string[],units:{id:string,label:string,depends_on:string[],operation_paths:string[]}[]}`; the Host still renders the complete byte/text diff and does not imply approval. `ProposalValue = {proposal_id:string,preview:HostChangePreview}`. `NarrativeChangeOperation` and `SourceEvidence` are exactly the bounded v1 objects accepted by `modules/story/src/narrativeChangeSet.ts:validateOperation` and `validateEvidence` at the pinned Scriptorium revision; the H0 common compiler contract binds their stable source IDs to the shared request scope.

## UI, execution and dependencies

### Desktop and Mobile

Narrative contributes a functional **Work Outline** to the Host's normal panel registry as `proprium.narrative.work-outline`, and a **Continue writing** command `proprium.narrative.continue-writing` to the existing writing surface. These IDs remain stable across artifact releases. It is not a new top-level tab and does not replace the Files browser. A non-work repository keeps Files as the primary tree and does not show an empty novel. For a new workspace, an explicit “Create first volume” action opens the Host form and submits a reviewed proposal.

The outline renders lazy expandable Volume → Chapter → Scene rows with title, selected scene, error/warning state and accessible move-up/move-down buttons. Root offers “Add volume”; a volume offers “Add chapter”; a chapter offers “Add scene”; a volume/chapter/scene row offers “Rename” for its structural title; a scene offers “Relink manuscript” to choose an existing workspace text file. Pointer drag is optional. Selection, tab order, keyboard activation, focus return and large-tree virtualization are supplied by Host components. Scene selection opens the resolved manuscript through the Host guard. A missing plugin leaves Files/editor visible and an explanatory unavailable contribution.

Desktop places outline beside the existing manuscript editor. Mobile puts **続きを書く** in the writing/home surface and opens the structure in a transient sheet; closing it returns to the same editor and caret. Reordering is available by buttons/menu as well as touch drag. Every panel switch preserves the editor instance, Japanese IME composition, selection, undo and scroll. A request that would replace the active document waits for the Host journal flush and dirty guard; if composition or storage cannot be safely settled, the Host keeps the current scene active and explains why.

The Host, not the plugin, shows Draft/checkpoint/publication states. A stale scene or deleted resume target is explained without inserting its Draft into another scene. Existing scratch is clearly separate from manuscript body. The Loom quick-write affordance may appear on Mobile: show the preceding three paragraphs read-only, edit an append buffer, and submit that buffer through the same Host editor document and Draft journal. **フルエディタで開く** remains available. No success state appears before the Host confirms local Draft journal storage.

The Host's existing reader renders Narrative's sentence reading marks as highlights and a list. Selecting an unmarked sentence opens a comment form; the comment is optional and limited to 200 UTF-16 code units. Selecting a current marked sentence removes that mark after a Host proposal; the list shows its stored snippet/comment and offers jump and explicit remove. In vertical-preview mode, mark interactions are unavailable and stored marks appear again when returning to horizontal reading. A stale mark is labeled and can be removed, but cannot jump to an unverified text range. Mark create/remove use ChangeSet review and never save or alter manuscript text. A dirty Draft remains readable and may be selected ephemerally, but persistent mark mutations wait until the Host locally saves/reconciles that Draft; the user sees “Save locally first.” After that explicit local save, the Host submits a fresh proposal pinned to the exact body hash and metadata revision. This does not trigger remote synchronization.

Mobile reading exposes next-scene navigation in volume/chapter/scene order. The Host uses the current tree revision: it checks later scenes in the current chapter, then queries subsequent chapters and volumes as needed through paged `hierarchy.tree`, and passes the next unique scene to `scene.open`; the final scene has no next target. Host applies the normal scene-navigation guard. Mobile Home scratch capture supports text and camera attachment in the Host journal, up to 8 files of 8 MiB each. The Host may reject a capture only when the browser's actual journal quota cannot retain it, and then does so before changing the journal with a visible `capacity` result. Voice recognition is a separate optional browser capability: show locality and permission/consent state before starting; omit it when transmission locality cannot be established. These are Host affordances because they complete the recovered author path; they do not become Narrative plugin storage or authority.

### Dependencies, lifecycle and distribution

P0 requires generic Host `workspace.identity.read`, paged `workspace.file.list`, revisioned/chunked `workspace.file.read`, typed `workspace.change.propose`, functional declarative `workspace.ui.contribute`, `workspace.navigation`, Host editor/recovery journal and plugin discovery/admission. The separate `workspace.change.stage` capability is needed only by the mixed-domain compiler flow above. H0 v2 defines these as targets; current v1 demo labels and 256-file snapshot do not satisfy Narrative requirements.

Optional providers: none for P0. Knowledge can later enrich scene context; Research, Diagnostics, Semantic and Speaker are not prerequisites to browse or type. The P1 reading-mark extension uses the same Host `workspace.file.read`, `workspace.change.propose` and Host-rendered reader/editor decorations; it requires no Knowledge or external provider. Knowledge is a caller of `hierarchy.tree`; Publishing may use that same read action to preserve chapter order; Paired Writing calls `changes.compile` as one owner compiler. These calls use the Host registry and create no reverse plugin dependency. Narrative never invokes another plugin. `workspace.change.stage` is required only when a caller supplies prior mixed-domain staged bytes to `changes.compile`; Paired Writing being absent disables only mixed-domain compatibility ingress, not P0 writing.

Narrative compute is a signed WASM Component Model/WIT artifact in a terminable Worker. Host-rendered forms, tree, sheets, quick-write, scratch, CodeMirror and reading UI remain trusted Host TypeScript. Narrative contributes schemas and typed actions, never React/DOM/CSS. It has no model/worker beyond its lazily started plugin Worker, no network egress and no required asset download. Install/admission checks the publisher, immutable digest, ABI, manifest capabilities and dependency graph. Disabled/uninstalled means no Worker; enabled-idle means metadata only; activation is lazy on a tree/scene action. Failure, timeout, cancellation or disable releases the Worker/cache lease without interrupting core editing or dropping a pending Host proposal.

## Acceptance

These gates are required to declare the Narrative product usable. Passing Scriptorium source tests proves only the legacy behavior named in provenance. Proprium implementation claims require browser tests with the installed signed artifact and the real Host editor.

<a id="accept-nar-a01"></a>

### <a id="nar-a01"></a>NAR-A01 — Work recognition and generic workspace

On a synthetic repository with two volumes, chapters and scenes, `work.detect` returns the scope-derived `work_id` and the paged outline reproduces the YAML IDs, titles, parent links, order and explicit manuscript paths. On a repository without these paths, Narrative returns `unrecognized`, the generic Files list remains usable and no fake empty work is shown. An empty repository can start by proposing its first volume. A repository with one malformed child returns that path diagnostic while valid siblings remain accessible; known paths with no usable volume return `malformed`.

<a id="accept-nar-a02"></a>

### <a id="nar-a02"></a>NAR-A02 — Scene selection opens the linked file

Select a scene whose `manuscript` points to a path different from the ID-derived convention. The Host opens that exact file in the existing editor and displays volume/chapter/scene location and both file revisions. The plugin does not return a full-repository snapshot or body. A duplicate scene ID reports every conflicting path using `ambiguous_identity`; no row silently wins. A nonexistent scene ID returns `scene_not_found`; an existing scene with a missing body returns `file_not_found` and a Narrative diagnostic.

<a id="accept-nar-a03"></a>

### <a id="nar-a03"></a>NAR-A03 — Continue and recovery scope

With a local resume record for author A/repository A, Continue opens its current scene and restores sentence/cursor/scroll only after journal reconciliation. Author B, another repository, branch or missing local workspace cannot receive that record. A deleted scene, changed manuscript path, missing body, corrupt position or stale revision yields an explicit stale/unavailable view and a manual tree choice; it never redirects the Draft to another scene. A pending unsaved Draft remains recoverable while the author inspects or cancels that choice. With no resume record, the UI offers the outline instead of inventing a “last scene.”

<a id="accept-nar-a04"></a>

### <a id="nar-a04"></a>NAR-A04 — Create volume, chapter and scene

From a generic empty repository, create a volume, then a chapter, then a scene. Review shows exact new paths and all affected files. Applying the scene proposal creates both the YAML record and the empty Markdown at its canonical path with `status: planned`. Insert at position two shifts every later sibling using current revisions; append leaves earlier orders untouched. Reject changes no file. Existing ID/path collision, invalid/missing parent, duplicate ID or stale tree rejects the proposal without partial output. Retrying an identical request returns the same proposal; reusing its idempotency key with changed title returns `idempotency_conflict`.

<a id="accept-nar-a05"></a>

### <a id="nar-a05"></a>NAR-A05 — Reorder with explicit approval

Reorder chapters within one volume and scenes within one chapter from keyboard controls and touch/pointer controls. The review names the exact siblings and changed order values. Approving at the expected tree revision changes only their `order` nodes and returns per-file revisions; rejection leaves source untouched. A stale revision, missing sibling, duplicate ID or partial sibling list is rejected. Attempt a raw cross-parent scene update or volume-order update and receive `invalid_input` with no proposal; no cross-parent drop, directory move or delete occurs.

<a id="accept-nar-a06"></a>

### <a id="nar-a06"></a>NAR-A06 — Structural metadata and Knowledge boundary

Read breadcrumbs and edit a scene title using its expected metadata revision; unknown YAML keys, comments, formatting and unrelated fields survive. Relink that scene to another existing Markdown path: review shows old/new links, neither body is moved/deleted/rewritten, and the editor opens the new path only after Host navigation guard. Attempt to change `pov`, `appears`, `mentions`, `location`, `goal`, or `conflict` through Narrative and receive `invalid_input`; those fields route to Knowledge. `readingMarks` is the explicit annotation exception but can be changed only through the dedicated reading-mark actions, not `structure.update`. Attempt `volume` or `chapter` changes through `scene.update` and receive `invalid_input`; no unsafe path, parent or order change is proposed. A stale title or link proposal is rejected with `snapshot_stale` and leaves the active manuscript and current Draft unchanged.

<a id="accept-nar-a07"></a>

### <a id="nar-a07"></a>NAR-A07 — Editor, draft and Host authority

On desktop Chromium and mobile WebKit, enter Japanese text with an active IME composition, selection, undo history and nonzero scroll. ### <a id="nar-a11"></a>NAR-A11 — Reading-mark recovery and revision safety

On Desktop and Mobile reader surfaces, display valid marks from a selected scene's `readingMarks` YAML field at exact zero-based UTF-16 offsets. Verify offsets after Japanese text and a surrogate-pair character; highlight and jump only when the current body slice equals the stored snippet. Add a mark to a selected sentence, enter an optional comment up to 200 UTF-16 code units, and remove a mark both by selecting the marked sentence and from its list. The Host review shows the exact scene YAML diff; approval updates only `readingMarks`, while rejection leaves metadata and manuscript bytes unchanged. The operation does not alter editor text, selection, undo history or a pending Draft.

Before adding, require the exact current saved-manuscript and scene-metadata revisions and verify `snippet === body.slice(offset, offset + length)`. Change either revision after the user selects the sentence and the proposal returns `snapshot_stale`; change the snippet/range or use a duplicate ID/span and receive `invalid_input`/`conflict`. With a dirty Draft, the mark can remain a transient selection but persistent controls say “Save locally first”; after explicit local save, a fresh mark request succeeds against the new body hash and metadata revision without remote synchronization. An existing mark whose excerpt no longer matches its body offset is visible as stale, cannot jump or auto-reanchor, and can be removed by ID after revision revalidation.

Load a legacy scene with valid marks plus an invalid row, an unknown field on a valid row, YAML comments and unusual quoting. `reading-marks.list` shows valid marks and path/index diagnostics for malformed entries. Add/remove another valid mark and review the proposal: every invalid row, unknown key, comment and unrelated byte remains intact. If the syntax-aware editor cannot preserve them, reject without mutation. Disable Narrative and confirm marks stay in the Git metadata while ordinary writing and navigation continue.

## Portable resume markers

| Feature | Source disposition and user-visible result | Acceptance |
| --- | --- | --- |
| NAR-12 <a id="feature-nar-12"></a> | `RECOVERY` of the per-device recent-scene/cursor intent in Scriptorium `app/src/resume/continueCandidates.ts:mergeContinueCandidates` and its tests; `DESIGN_TARGET` for an explicitly reviewed Git marker replacing server-held cursor state. After an author publishes a marker, another device that synchronizes that Git snapshot can offer the same scene/position. P0 local resume never waits for it. | [NAR-A12](#accept-nar-a12) |

The old server's recent-device cursor store is not restored. Its user-visible continuation intent is preserved through optional author-approved Git state at `meta/proprium/plugins/proprium.narrative/resume.v1.yaml`, with `{schemaVersion:1,positions:[{deviceId,repositoryId,branch,sceneId,manuscriptPath,manuscriptRevision,sentenceIndex,scrollTop,updatedAt}]}`. `deviceId` is a Host-generated opaque per-browser UUID, not an author identity or credential; `repositoryId` must be the bound positive numeric GitHub identity. `sentenceIndex` is null or a positive one-based integer under the same Host sentence mapping as local resume, `scrollTop` is finite/nonnegative, and `updatedAt` is Host-issued ISO-8601 UTC. One current entry per device/repository/branch is permitted; preserve all other entries and unknown YAML/entry fields. Conflicting duplicates are explicit `ambiguous_identity`, never silently overwritten. The record contains no manuscript/draft text or browser journal. Local-only unbound workspaces retain local resume and cannot claim portable publication.

`proprium.narrative.resume.marks.list` is `read`, input `{cursor?:string,limit?:1..100}` (default 50), output `{items:[{device_id,scene_id,title,manuscript_path,manuscript_revision,sentence_index,scroll_top,updated_at,availability:ready|stale|missing,publication:local_only|remote_confirmed}],next_cursor,source_revision}`. It reads only the selected snapshot and Host-confirmed publication provenance; absent file is an empty list with null revision, malformed file is `unsupported_format`. An entry is `ready` only if repository/branch, scene ID, explicit path and body revision match; a changed body is stale and never repositions the current draft. The Host merges these with its local resume view, preferring its own recoverable local position for the same scene; other devices remain individually labeled. The existing `scene.continue` contract validates a selected marker converted to `ResumePosition` with null draft generation. No read navigates automatically.

`proprium.narrative.resume.mark.propose` is `propose`, descriptor `callers:[ui]`, `requires_user_gesture:true`, input `{scene_id,expected_manuscript_revision,expected_marker_revision:string|null,sentence_index:integer|null,scroll_top:number}`. Host verifies that the position is the current displayed saved document and supplies device ID/time; arbitrary caller cursor/identity substitution is denied. Dirty draft returns `dirty_draft` with a Save locally first path, retaining cursor and form. Output is the common `{proposal_id,preview}` for one YAML metadata unit, with exact manuscript/scene/marker read revisions and absent-path precondition when new. It updates only that device's entry. Standard idempotency/cancel/stale/no-loss rules apply. Local apply/checkpoint does not mean another device can see it; explicit Host publication and subsequent synchronization are required. No automatic cursor commit, push, cross-device draft recovery or server is introduced. This portability extension follows P0 and can be implemented alongside P1; it does not block local continue-writing.

### NAR-A12 — Portable resume markers

Use two browser profiles bound to one synthetic repository/branch. Publish a marker from a saved scene through proposal → Host review → local apply → explicit checkpoint/publish; before remote confirmation label it local-only. Synchronize the confirmed Git snapshot on the second profile: the correct device-labeled scene and sentence become an optional Continue candidate. Another repository, branch or device's unsaved text cannot be rebound. Modify the manuscript after marking: the old position is stale and cannot move the caret; local recoverable draft wins over a remote candidate for the same scene. Offline/missing marker leaves local resume usable. Repeated proposal returns one receipt, stale marker/body revisions fail, rejection writes nothing, unknown YAML entries survive, and Mobile selection/return keeps IME/undo/draft intact. No server cursor store, hidden publication or cross-device journal promise is permitted.
