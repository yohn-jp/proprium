# Canon P1 — `proprium.knowledge` (Bible, Relations and Story State)

**Product job:** Help an author keep the facts, people, places, objects, rules, relationships and promises of a long work coherent, and inspect what has changed by a selected scene. The plugin interprets ordinary Git files; Proprium Core remains a generic Git workspace. The contract below is the implementation target. The legacy Scriptorium module and Arcadia Loom application are source evidence, not a shipped Proprium plugin.

Knowledge owns the structured Bible and its projections. Narrative owns the volume/chapter/scene tree and manuscript navigation. Host owns repository identity, revision reads, editor state, approval, file application and Git. A Knowledge panel can ask the Host to open an entity or scene, but it cannot mount or replace the editor.

## Scope and partition

Knowledge provides entity and relation reference, nested notes, thread lifecycle, graph/map/timeline views, objective world state and reader-disclosure evidence. It accepts local author proposals for Bible notes, scene references, world-state events and candidate suggestions. It does not own scene creation/reordering, manuscript text editing, editor extensions, generic ChangeSet review/apply, dialogue attribution or voice evaluation, search/index services, publishing, Git or model execution.

The eight official plugins remain separate for these reasons:

- Knowledge groups Bible, relations, threads and time-indexed state because they share the same Git facts and evidence links. Graph, map and timeline are projections of that data, not separate plugins.
- Research owns the reusable lexical index, term registry and tokenizer. Knowledge may consume its declared tokenizer result for tag candidates.
- Semantic owns optional embeddings and reranking. It can offer candidate evidence to Knowledge, but basic Bible, thread and state views work without it.
- Speaker owns attribution corrections and voice evaluation. Authored voice fields remain part of a character entity, exposed here as data.
- Diagnostics consumes Knowledge facts as an optional provider; Knowledge does not depend on its warning implementation.
- Paired Writing owns generic context manifests and `ChangeSet` submission. Knowledge emits typed proposals to the Host action registry; no plugin calls another plugin's private implementation.

The dependency DAG is in [the shared architecture](../ARCHITECTURE.md). The official Knowledge plugin is P1 after H0 and requires Narrative's scene identity/path provider; if that dependency is absent or disabled, Host reports Knowledge unavailable instead of advertising a reduced official plugin. Bible parsing, entity CRUD and graph algorithms can be developed and verified against repository snapshots without Narrative, but the installed user-facing plugin does not claim scene-context, appearance or navigation parity until Narrative is active. Generic Git editing remains available through the Host.

## Data contract

### Canonical Git files

Knowledge reads these paths from one Host-pinned repository snapshot. Existing paths and IDs remain the source of truth; a missing directory is an empty collection, malformed files are reported as data errors, and duplicate IDs are ambiguous rather than last-write-wins.

| Data | Canonical paths and fields |
| --- | --- |
| Character | Existing records may be flat `bible/characters/<id>.yaml` or `.yml`, or nested `bible/characters/<id>/profile.yaml`; preserve each existing path and never duplicate a record during migration. The default path for a new nested record is `profile.yaml`. Optional sibling `voice.yaml` is authored character metadata merged into the read projection as `raw.voice`. Stable `id`, `name`, `aliases`, `tags`, `status`, `notes`, relations and all additional keys are retained. |
| Places, items, factions, events, lore, dialogue sketches | `bible/locations/*.yaml`, `bible/items/*.yaml`, `bible/factions/*.yaml`, `bible/timeline/events/*.yaml`, `bible/lore/*.yaml`, `bible/dialogue_sketches/*.yaml`. Keep each file's path, `id`, `type` when present and unknown fields. |
| Threads and arcs | `plot/threads/*.yaml` and `plot/arcs/*.yaml`; preserve `keywords`, `status`, `resolution`, relations, notes and unknown fields. A declared status is source data; computed lifecycle is a separate read result. |
| Scene references | Existing scene YAML under `plot/volumes/<volume>/chapters/<chapter>/scenes/*.yaml`. Read `pov`, `location`, `appears`, `mentions`, `relations`, `threads` and `manuscript` links as authored. Narrative owns hierarchy and the exact scene-to-Markdown mapping. |
| Objective events and effects | Existing scene YAML fields `effects` and `state_events`. `effects` are source-declared rules; `state_events` hold author-confirmed events and their source/evidence/status metadata. Do not write a derived snapshot into either field. |
| Tag categories | `meta/tags.yaml`, read-only to Knowledge. Author tag membership is the entity's existing `tags` field. |
| Structured notes | The entity's existing `notes` field: `{lead: NotesBlock[], sections: NotesSection[]}`. A block is `{type:"paragraph",text}`, `{type:"definitions",items:[{term,description}]}` or `{type:"steps",items:[{term,description}]}`; sections have `heading`, `body`, and recursive `children`. Legacy text forms remain readable. |

A dialogue sketch is a standalone Bible asset at `bible/dialogue_sketches/<id>.yaml`, not a scene or manuscript. Its known fields are `{id,type:"dialogue_sketch",title,situation?,participantEntityIds:string[],lines:[{speakerEntityId,text}]}`. `id` uses the `ds-` prefix; `participantEntityIds` are unique, existing character IDs. Each ordered line has nonempty text and a speaker ID selected from the participant set. The line array order is the authored order; lines have no independent persistent IDs, so editing or reordering proposes replacement of the full `lines` value under the entity file revision. Unknown top-level and line keys are retained losslessly; the editor changes only the known fields. An unresolved or removed speaker remains visible as a broken reference and must be explicitly corrected before a line edit can submit.

A confirmed `StateEvent` in `state_events` has `{sceneId,order,kind,subject,object,payload,source,eventId,status}` and optional `propositionId`, `evidence`, `confidence`, `createdAt`, `replacesEventId`. `kind` is `location|acquaintance|ownership|knowledge`; `object` is a stable entity ID or null; `source` is `rule|llm-draft|manual`; confirmed rows have `status:"confirmed"`. `evidence` items are `{sceneId,excerpt?,startOffset?,endOffset?}` with half-open source offsets. A proposal event carries the same identity/evidence fields with `status:"proposed"` and is never folded into objective state until the corresponding Host-reviewed operation appends a confirmed row.

`StateProposal` is `{id,event,manuscriptHash,status,conflictEventIds,duplicateOfProposalId,history,createdAt,updatedAt}`; status is `proposed|stale|approved|rejected`, and history rows retain `{action:"created"|"edited"|"approved"|"rejected"|"stale",at,event}` plus unknown fields. `ZukanSuggestion` is `{id,entityId,blockPath,proposedText,evidence:[{quote,sceneId?}],status,source,kind,sourceId?,sourceRange?,sourceRevision,confidence?,createdAt,updatedAt,sourceHash?}`; status is `pending|approved|rejected|stale`, source is `manuscript|dialogue-sketch`, and kind is `fact|dynamic|habit|null`. A dialogue-sketch `sourceRange` is `{start,end}` 0-based inclusive line indexes; a manuscript source is cited by scene ID and exact manuscript/sketch revision. Preserve additional stored history fields when reading or rewriting a row.

The source uses IDs such as `char-*`, `loc-*`, `item-*`, `faction-*`, `event-*`, `thread-*`, `arc-*`, `lore-*` and `ds-*`; old valid IDs are never regenerated from a changed display name. A create may include an explicit safe ID; otherwise it uses the type prefix and the Scriptorium-compatible hint rule: NFKC-normalize, lowercase, replace non-ASCII alphanumeric runs with `-`, trim `-`, cap the hint at 48 characters, and suffix collisions with `-2`, `-3`, etc. An empty hint starts at `<prefix>1`; exhaustion returns `capacity` rather than a time-based ID. A stable ID is repository-local. A repository ID, legacy project ID, entity ID and series ID are distinct types.

### Proprium-owned metadata and legacy data

New Knowledge metadata, when it is canonical author data, lives below `meta/proprium/plugins/proprium.knowledge/v1/`:

- `series.yaml` is the series registry in the selected Bible repository.
- `series-binding.yaml` records this work's `{seriesId,bibleRepositoryId?}` binding when a verified stable repository identity exists. `bibleRepositoryId` is only the positive GitHub numeric ID; never write Host `workspace_id`, legacy project IDs or an invented ID here. For local-only/unbound repositories, the user selects a Host-registered binding again on each device; Host may retain that choice in local `plugin.preferences` keyed by the binding-record fingerprint, but it is not Git authority. The registry does not duplicate a member-repository list; work membership is represented by work bindings.
- `state-proposals.jsonl` records source-backed candidate state events and decision history until they are accepted, rejected or stale.
- `zukan-suggestions.jsonl` records evidence-backed proposed notes additions and their decision state.

These files are ordinary Git source. A change to them is a Host-reviewed proposal. No proposal becomes canonical merely because a worker produced it. The series Bible and bound work files are independently authoritative repositories; overlay results cite both selected revisions.

Legacy `meta/scriptorium/modules/story/{state-proposals.jsonl,zukan-suggestions.jsonl,v1/series.json}` and any imported `.arcadia` or SQLite data remain readable/preservable recovery inputs. The plugin must not write new data into the retired namespace, erase unknown legacy fields, equate `projectId` with Git `repositoryId`, or silently bind an unresolved legacy ID. Migration is a separately reviewable ChangeSet with source hashes, original values and explicit unresolved-ID markers. If no migration is approved, the bytes remain available at their existing paths.

### Revision and derived data

Every action uses the common v2 `ActionRequest` and `ActionResult` envelope in [Host/Plugin Contract](../HOST-PLUGIN-CONTRACT.md): Host supplies `request_id`, `scope`, pinned `snapshot`, deadline and optional `idempotency_key`, and wraps the action value or typed error with that same observed scope/snapshot. The plugin does not accept a caller-selected current repository or silently fetch another one. Reads return source paths and SHA-256 file revisions; entity revisions are hashes of the selected entity bytes. Every proposal is a common Host-owned `ChangeSet` with a unique-path `read_set`, complete source evidence, absence preconditions for creates, ordered dependency-DAG units, stable operation IDs and exact file contents/content artifacts. These are logical contract fields; the current Proprium WIT v1 is not claimed to implement them.

Entity listings and overlays must be paged through Host file reads. Graphs, mention dictionaries, timelines, lifecycle calculations, candidate scores and caches are derived. A cache key includes repository, branch, snapshot/worktree generation, selected Bible snapshot (if any), source file revisions and algorithm/schema version. Cache loss or corruption rebuilds from source. It never changes Git data. Search indexes belong to Research; vectors belong to Semantic.

### References and overlay rules

Relations are read from the supported scalar/list forms in existing YAML (`appears`, `mentions`, `pov`, `related`, `affiliated`, `target`, `first_appears`, `planted`, `payoff`, `plants`, `advances`), `relations: [{target,kind,note?}]`, and supported nested `entities`/`threads` forms. Preserve relation kind strings that an older reader does not recognize. Resolve references by stable ID and keep source path/revision. A missing or duplicate target appears as a broken-reference diagnostic; it is never silently re-targeted by name.

A series overlay is read-only. For a GitHub binding to a verified `bibleRepositoryId`, or a local-only binding explicitly reselected by the user in Host preferences, the work entity with the same ID takes display precedence over the Bible entity; output still includes both records and their provenance. Links are unioned and deduplicated by `(from,to,kind)` only. Duplicate IDs within either repository, unresolved endpoints, stale snapshots and legacy project IDs remain explicit conflicts. The plugin never copies Bible files into a work, writes to an inactive Bible repository, rewrites an unselected series source, or resolves a binding by repository name.

Linked repository reads require the Host's explicit `workspace.repository.snapshot.read({workspace_id,repository_id,branch,snapshot_id})` capability for a user-selected, Host-registered local binding. Host pins that workspace and grants only read leases; the target source snapshot is included in overlay results and revalidated if a proposal cites it. No persisted binding may impersonate Host `workspace_id` or infer a repository from a display name. There is no plugin network egress, automatic clone/fetch or Gateway dependency. If the Bible workspace or pinned bytes are not available, work-local Bible functions continue and the overlay reports `repository_unavailable` or `file_not_found` with a retry/open path.

## Public action contract

The IDs below are the stable Proprium action IDs. The Scriptorium IDs in the provenance ledger are source names only. Plugin guest effects are `read` or `propose`; there is no guest `apply` or `approve` effect. Every invocation and result uses the common `ActionRequest` / discriminated `ActionResult` shape in [Host/Plugin Contract](../HOST-PLUGIN-CONTRACT.md); each output below is the `value` inside `{ok:true,...}`. A proposal action returns its Host-owned proposal reference and preview only. Its Host-issued `idempotency_key` is on the request envelope, not an action input, and is mandatory for every `propose` invocation. The plugin builds stable operation IDs in the common `ChangeSet`; the same key and request digest returns the original proposal, while a changed digest returns `idempotency_conflict`. Inputs reject unknown keys, malformed IDs, wrong types and over-limit payloads.

`expectedEntityRevision`, `expectedSceneRevision`, `expectedCollectionRevision` and other `expected*Revision` inputs mean the exact source file or collection SHA-256 shown to the author within the Host-pinned snapshot. The relevant operation lists every source path/revision (including null for create) in `ChangeSet.read_set`; each unit contains generic `create|replace|delete` operations with exact bytes or a sealed artifact reference. Reads are repeatable for the same pinned snapshot. Host cancellation before apply prevents apply; during a Host write it waits for the recoverable unit boundary and reports the actual receipt. Cancellation never deletes or rewrites a pending proposal or editor recovery record.

`EntityType`, `BibleEntityType`, `EntityCreateValues`, `EntityPatch`, `DialogueSketch`, `DialogueSketchLine`, `EntityCard`, `FileRevision`, `StateProposal`, `ZukanSuggestion`, `ProposalStatus`, `KnowledgeNarrativeOperationV1`, `NarrativeEvidenceV1`, `ReadSetEntry`, `GenericUnit` and `CompileDiagnostic` are versioned schemas generated from this canon and the shared contract into the v2 action registry/WIT bindings. `DialogueSketchLine` is `{speakerEntityId:string,text:string}`; `DialogueSketch` is the path-backed object specified under Canonical Git files, with `id`/`type` immutable during update. The table above is the normative action payload and value shape; validators reject unknown request keys. Existing unknown source keys are different: retain them byte/field losslessly in every update preview and operation. Guest action `knowledge.entities.create/update` are the sole CRUD implementation for dialogue sketches; the dedicated UI view does not define a second entity writer.

`KnowledgeNarrativeOperationV1` uses the pinned NarrativeChangeSet v1 field vocabulary `{id,evidenceIds,assessment,kind,precondition,target,...}`, with `assessment:{confidence:0..1,risk:"low"|"medium"|"high"}` and `precondition:{kind:"revision"|"content-hash",value:string}|{kind:"absent"}`. Accepted kinds and exact kind-specific fields are: `entity.create` (`target:{entityId,entityType}`, `precondition:absent`, `values:JSON object`); `entity.update` (`target:{entityId}`, `changes:JSON object`); `scene.update` (`target:{sceneId}`, `changes:JSON object` containing authored semantic/state metadata, including references, `effects` or `state_events`; reject `id`, `type`, `volume`, `chapter`, `order` and `manuscript` keys so Narrative owns structure and manuscript mapping); `state.append-event` (`target:{sceneId,eventId}`, `event:StateEvent`, optional `sourceProposal:{id,manuscriptHash}`); `thread.link-scene` (`target:{threadId,sceneId}`, `relation:"planted"|"payoff"`, optional `note`); and `reference.link` (`target:{from,to,kind}`, optional `note`). `thread.link-scene` relation `advanced` is not recovered as supported by Scriptorium's builder; a valid authored `advances` direction uses `reference.link`. Evidence records are `{id,sourceKind:"manuscript"|"entity"|"scene"|"diagnostic"|"state-proposal"|"external",sourceId,revision,range?:{start,end}}`; ranges are nonnegative integers with end greater than or equal to start, and every `evidenceIds` item must resolve to one record. For `entity.update`/`scene.update`, omitted fields are preserved, explicit `null` deletes a field, and `id`/`type` cannot change. Reference values must resolve uniquely in the current staged view and their original file revisions enter the base read set. Source operations must have unique IDs and targets within this compiler call, and the input keeps Scriptorium's 1 MiB / JSON-depth-16 / 10,000-node bounds. The optional `staging_snapshot` is a Host-issued opaque string for the same original scope/snapshot, overlaid with preceding ordered generic operations. Read results are deterministic for a pinned base/staging snapshot; only source order affects sequential composition.

Every action descriptor uses `schema_version:1` and explicit `effect` from the table. Pure `read` and `propose` actions are callable by `ui`, `mcp` and `plugin` callers with the current Host-selected workspace scope; `requires_user_gesture:false`. The compilation-only `proprium.knowledge.changes.compile` descriptor is restricted to `callers:["plugin"]` and is invoked by Paired Writing through the Host action registry. Navigation, provider requests, downloads and preference edits are not Knowledge actions. Optional provider requests require their own Host UI gesture and consent, and no Knowledge action can smuggle that effect through `read`.

### Stable errors, retry and source drift

Map errors to the Host taxonomy in [Host/Plugin Contract](../HOST-PLUGIN-CONTRACT.md), including `invalid_input`, `unsupported_schema`, `invalid_path`, `file_not_found`, `unsupported_format`, `ambiguous_identity`, `snapshot_stale`, `dirty_draft`, `conflict`, `scene_not_found`, `capability_denied`, `missing_capability`, `dependency_unavailable`, `provider_unavailable`, `repository_unavailable`, `repository_not_active`, `capacity`, `cancelled`, `timeout`, `guest_trap`, `storage_unknown` and `idempotency_conflict`. `entity_not_found`, `broken_reference` and `author_review_required` are `details.kind` values or visible diagnostics, not alternate Host error codes; they do not authorize a fallback write. Include the exact source path, snapshot and retry/recovery path when applicable.

A missing file in an optional source directory is an empty collection. A malformed YAML/JSONL file, duplicate entity ID, missing referenced file, oversized page or invalid range yields a visible typed failure with the path and selected snapshot. No exception is converted into a successful empty graph. When source content changes after a result, navigation, note edit, proposal creation or approval, the Host returns `snapshot_stale`/`conflict`; the UI offers refresh/re-evaluate while retaining the author draft.

For every `propose` action, the same request-envelope `idempotency_key` and canonical request digest returns the existing proposal/receipt. The same key with changed input returns `idempotency_conflict`. After a lost response, the caller queries the Host proposal by ID before retrying. A proposal is never replayed as a new write based only on a cached derived result. `cancel` does not cancel a user-owned Host proposal or editor recovery record.

- **Thread review**: cards show declared status separately from computed planted/advanced/resolved state, cited scenes, unresolved payoff, last mention distance and warning reason. “Open scene” requests the Host to navigate to the referenced scene and source Markdown. ### Dialogue-sketch assets

**Required Host capabilities:** revision-pinned paged file list/read; selected-work identity; typed Action Registry; proposal/review/apply; actual Host-rendered lists/forms/detail/graph/map/timeline widgets; guarded navigation; derived-cache lease; request cancellation and typed capability errors. **Required plugin dependency:** Narrative's stable scene identity/path provider. No Gateway, login, remote service, external model, network egress, WebGPU or model file is required.
