## Proposed first independent leaf and sequence

The smallest independent leaf to evaluate first is **C02: cursor-only sentence-position work**, isolated to `ManuscriptInput` and its sentence-position helper. This is a candidate, not an implementation decision: W0 has a strong size-correlated arrow workload, while W1's compact summary does not retain an after-W1 arrow cohort. The leaf does not require changing `SharedApplication` or the journal and can be checked against the existing source sentence-numbering tests. The internal optimization remains undecided until G0's profile distinguishes string materialization from segmentation work.

1. Wait for G0 to record the W1-integrated source SHA, host/toolchain, fixture, and focused browser baseline. Do not reuse W0 as the current before value.
2. On the same synthetic small fixture, capture 1 KiB / 100 KiB / 1 MiB typing and arrow cohorts, React commits, Long Tasks, strict IDB reads/writes, CPU profile, and endpoint memory using the checked-in browser harness. Retain raw output; report sample counts and the p99-as-maximum limitation.
3. If the latest profile confirms a repeatable cursor-path cost, make one C02-only change in `ManuscriptInput.tsx` / `continueCandidates.ts`; add exact-output coverage for Japanese punctuation, dialogue, multiline text, selection, and restore. Keep C01 text reuse unchanged. If no isolated benefit is established or exact mapping cannot be preserved, record C02 as measured/no change.
4. Compare before/after on the identical fixture and browser. Review input and arrow latency together with commits, Long Tasks, IDB activity, and memory. Do not accept a cursor gain that shifts cost or changes recovery/editor behavior.
5. Only after the C02 result, evaluate remaining candidates in local leaves. C01/C04/C13 begin as W1 residual evaluation; do not reimplement them. Any journal schema, transaction, queue, or scene-freshness change requires its focused failure and race coverage before the common G1 verification gates.

The browser harness commands require a built Core profile and a fresh synthetic directory; they must run only after the G0 measurement lease is released. Candidate-specific coverage for scene switch/layout changes should use the corresponding modular-workspace acceptance tests. Journal representation or queue changes also need exact two-tab, quota/error, recovery, and checkpoint-while-newer-text tests. After any accepted code leaf, apply the G1 checks in [CORE-64-GOAL.md](CORE-64-GOAL.md): frozen install, typecheck, unit tests, Core build, and `audit:core`; run Chromium acceptance for changed browser paths. Full-profile build and OCI checks apply only if a leaf changes runtime/profile/dependency or OCI production paths. None of these checks were run here.

## Ownership and handoff boundaries

- G1 has one integration owner for [`SharedApplication.tsx`](../../app/src/application/SharedApplication.tsx). That owner also coordinates any accepted G1 `SceneEditor.tsx`, editor, workspace, or journal leaf so no G1 worker edits the shared application path concurrently.
- The proposed C02 leaf is limited to [`ManuscriptInput.tsx`](../../app/src/editor/ManuscriptInput.tsx), [`continueCandidates.ts`](../../app/src/resume/continueCandidates.ts), and [`continueCandidates.test.ts`](../../app/src/continueCandidates.test.ts), plus only the focused browser regression needed to prove the path. It is independent of SharedApplication integration.
- C07–C09 code may span `SharedApplication.tsx` (panel producer) and `Workspace.tsx` (catalog/layout consumer); keep both edits under the same G1 integration owner. C12–C16 storage work stays in `storage/journal.ts` and its tests, with G1 owning any corresponding `SharedApplication.tsx` call-site integration.
- G3 may own `app/src/resume/useRecentActivityResume.ts` and its direct tests for C38–C44 polling/bootstrap work, provided it keeps the existing hook contract and use sites intact. G3 does not edit `SharedApplication.tsx`: its timer, visibility, foreground-refresh call sites, and any hook wiring remain queued for the G1 integration owner. If G3 needs a changed hook contract or a SharedApplication call-site edit, it should hand off the isolated hook and requested interface change for sequential G1 integration after its leaf is ready.

## Code-contract declines

The following are ruled out independent of future performance measurements because they would violate the current contract: weakening strict IndexedDB completion or reporting an unconfirmed draft as stored; removing Draft → Checkpoint → confirmed Publish stages; bypassing complete `ChangeOperation` validation or its ID/generation/read/write/revision bindings; replacing scene-switch flush/freshness checks with speculative reads; allowing stale/equal-generation foreign operations to overwrite recovery data; and treating page exit as a durable asynchronous-write guarantee. C06 responsibility extraction and C11 editor-view lazy loading remain deferred until their own measurements identify a local benefit. These are boundaries on possible solutions, not final C01–C19 ledger decisions.
