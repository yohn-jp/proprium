# Core Wave 1 — Editor and Journal

This branch addresses Wave 0 candidates C01, C04 and C13. It keeps the Core journal as the strict IndexedDB recovery source, retains the existing 350 ms save schedule, and reduces editor work and post-save journal reads without changing the Git, checkpoint, publication, or single-writer contracts.

## Changes

- **C01 — CodeMirror text reuse:** a document-changing CodeMirror update serializes the new document once and reuses that string for the text and cursor-position callbacks. Selection-only updates still read the current document when needed.
- **C04 — editor notification isolation:** the editor continues to publish authoritative text immediately to `workRef` and schedule IndexedDB writes on the original timer. React publication is coalesced, and pending durability status is isolated in small memoized descendants so that a status-only update does not reconcile the manuscript and preview tree. Print, history and external text revision actions consume the newest editor value. Restore removes the captured draft timer and guards the captured repository/path/scene/author/operation before compensating a failed deletion; a late completion cannot delete or resurrect another context's draft.
- **C13 — local journal merge:** after a strict draft write succeeds, the UI merges that exact record instead of re-reading the full operations store. The merge is limited to the same document and author, removes only older editable drafts, and preserves newer, equal-generation-different-operation, foreign-author and protected records. Durability completion is bound to the same navigation, author, entry key, state and text. Explicit/foreground refresh remains the authority for full journal and proposal inventory; this change does not add immediate cross-tab notifications.

The new same-origin two-tab browser regression opens the same scene in one Playwright context. Tab A durably saves generation 1, then stale tab B attempts a different operation at the same generation. The test asserts that A's bytes remain in shared IndexedDB, B retains its text with an unconfirmed/error status, and B cannot checkpoint that unconfirmed draft. Existing recovery coverage also exercises print/history reads during the coalescing window, restore to the unchanged React value, delayed draft deletion, checkpoint completion while newer text is typed, author isolation, rebase, crash recovery and multi-document drafts.

## Performance evidence

The [canonical summary](results/wave1-editor-journal/summary.json) and [tables](results/wave1-editor-journal/tables.md) use the unchanged Wave 0 `summarizeBrowser()` cohort filters. The fixture is the Wave 0 ten-file small dataset (1,152,477 total bytes), with 1 KiB, 100 KiB and 1 MiB manuscripts. Chromium was 155.0.8059.79, the browser harness SHA-256 was `02e9a6fd44b56e25390ecc8a61591e2899446b3c424cec1ce57a189779f7a087`, and all raw snapshots report complete execution. Wave 0 base was repeated once to expose run-to-run variation.

At 1 MiB, Wave 0 base typing was 596.2/641.0/645.5 ms p50/p95/p99; its repeat was 575.6/663.1/694.5 ms. C01 produced 579.4/599.1/603.2 ms and 592.6/622.9/634.8 ms across two captures. This is a modest, noisy latency result: p50 overlaps the base captures, and the C01 end-of-input renderer RSS was 6.53–6.65 GB versus 5.46–5.48 GB at base. After the 35-second visible idle, renderer RSS was 407–420 MB and JS heap was 38.49–38.51 MB, close to the base post-idle boundaries. The endpoint RSS increase is recorded as a real tradeoff; it is not a continuous peak measurement.

C04's final isolated capture reduced 1 MiB typing to 513.2/536.7/547.4 ms, compared with 596.2/641.0/645.5 ms at the first base capture. The 100 KiB case fell from 59.2/68.5/68.6 ms to 51.6/56.8/59.2 ms, with React commits decreasing from 30 to 11; the 1 KiB case decreased from 31 to 15 commits. At 1 MiB, however, React commits rose from 56 to 92 and Long Tasks from 63 to 73. The endpoint-to-endpoint CDP TaskDuration delta fell from 35.276 s to 33.012 s, but it includes scene-open/cursor setup between the phase snapshots. The 1 MiB end-of-input renderer RSS increased by 906,612,736 bytes (5,475,459,072 to 6,382,071,808); after 35 seconds visible idle it was 409,309,184 versus 405,692,416 bytes, with JS heap 38,520,820 versus 38,704,812 bytes. Final C04 small-short control is `NOT_CHECKED`.

The first C04 coalescing-only design at `cfbe35f4` was rejected. Its canonical 1 MiB result was 595.7/640.2/643.0 ms, 88 React commits and 87 Long Tasks, versus the preceding C01 final capture at 592.6/622.9/634.8 ms, 57 commits and 63 Long Tasks. It did not improve the input cohort and increased commit and Long Task counts. The final C04 design at `d553df09` moved pending durability state into a separate status boundary and superseded that version. The rejected capture is recorded here as a diagnostic outcome; it is not part of the permanent raw archive.

C13's single final capture reduced IndexedDB reads from 74 to 31 and returned records from 93 to 28 in the 1 MiB input phase: 43 fewer reads (58.1%) and 65 fewer returned rows. The reductions also appear at 1 KiB (8 reads/3 rows to 4/1) and 100 KiB (6/5 to 2/1). This direct I/O reduction supports retaining C13 despite the 1 MiB input cohort worsening from C04's 513.2/536.7/547.4 ms to 521.8/551.1/620.7 ms, with commits increasing from 92 to 100 and Long Tasks from 73 to 77. Strict-write samples were 22 for C04 and 23 for C13 because autosave timing varies; their p50/p95/p99 values are not fixed-rate comparisons. The C13 end-of-input renderer RSS was 4,304,035,840 bytes and JS heap was 154,861,484 bytes; after idle they were 395,542,528 and 37,398,872 bytes. These are one-run boundaries and do not establish that C13 caused a memory reduction.

The C04/C13 p99 rows have only 20 key samples, so p99 is the maximum. C04/C13 each have one browser worker capture. CPU values are endpoint differences between `input.102400` and `input.1048576`; pure phase-local CPU is `NOT_CHECKED`. Component render durations, continuous browser memory peaks, native OS IME, 24-hour soak and offline/crash load are also `NOT_CHECKED`. Browser E2E ran Chromium only with the Core profile; it did not run full-profile contribution tests or WebKit.

## Raw measurement archive

Raw browser JSON and selected CPU profiles are compressed reproducibly by `scripts/performance/artifacts.mjs` and stored as a GitHub Release Asset. Git contains only compact summaries and the SHA-256 manifest; no raw `.gz` files are committed. The [manifest](results/wave1-editor-journal/INDEX.json) links the immutable [archive asset](https://github.com/yohn-jp/scriptorium/releases/download/perf-wave1-editor-2026-10-20/scriptorium-wave1-editor-2026-10-20.tar) and records the archive, compressed-file and source-file hashes. The release is `perf-wave1-editor-2026-10-20` (prerelease, not latest).

To verify the published archive, first download it and run `node scripts/performance/artifacts.mjs verify-archive docs/performance/results/wave1-editor-journal/INDEX.json <download-directory>`. Extract only after the archive hash passes, then run `node scripts/performance/artifacts.mjs verify docs/performance/results/wave1-editor-journal/INDEX.json <extracted-directory>` to check each compressed and uncompressed payload. The full retrieval procedure is in [the performance harness README](../../scripts/performance/README.md#external-baseline-evidence). Repackaging uses the existing tool's gzip and ustar settings and fails if any source bytes or hashes differ.
