## Sequencing and validation

1. Wait for G0's updated post-W1 baseline and release of its benchmark/full-check lease. Reconcile the current branch with that baseline before implementation.
2. C39’s measured hidden request and stale-response behavior justify the independent leaf in `useRecentActivityResume.ts`; keep `SharedApplication.tsx` with G1. C40’s measured debounce and `updatedAt` results justify retaining its existing write semantics.
3. Keep C41 and C42 as separate API decisions. C41 retains its before/after authority check; C42 requires per-phase cost and crash/recovery evidence before any storage change.
4. Schedule C46/C47 together with G5 build/entrypoint ownership after the repeat-load experiment. C38, C44, and the client half of C43 remain G1-coordinated. C64 remains G5.

For any code-bearing leaf, follow the fixed goal's required checks: `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test`, `SCRIPTORIUM_PROFILE=core pnpm build`, and `pnpm audit:core`. Use the focused commands and scenario evidence in the candidate table; for production browser/static-path changes also run the documented browser acceptance (`pnpm test:e2e`) and local OCI acceptance (`bash scripts/verify-oci.sh`). The focused C39/C40 browser acceptance is recorded in the result bundle; the broader required checks remain assigned to the verification batch.
