## C55 — late callback failed the abort invariant

The focused test reached the real host’s deferred author-change path. Before resolving the old mount, assertions passed that the mount authors were `author-old` then `author-new`, the old signal had aborted, the new contribution had one active set of resources, and the deferred old mount had not yet disposed. After resolving the old mount, the callback attempt completed and dispose ran. The assertion expected the callback outcome `rejected`, but the browser reported `resolved`.

The fixture’s `journalWrites` assertion followed the failing outcome assertion, so Playwright did not emit the captured metrics array. The observed callback result establishes that the old callback was not rejected after abort. Source inspection shows the in-process write path it takes: `context.propose` calls `journal.putProposal(snapshot.repository, authorScope, submitted)` before awaiting the API, then journals the API result using that same captured scope. The route fulfills the proposal request successfully. It is therefore an inference from the executed resolution and source order that the callback wrote into `author-old`; this run did not preserve an emitted write count. The harness has since been adjusted to attach all metrics before any assertion, so a follow-up run can show the array directly.

The key C55 observations are distinct. A callback first invoked after abort made zero journal writes and zero proposal requests. A write held before its real IndexedDB transaction completed then released after abort inserted one old-author record; the host removed exactly that record and made no proposal request. A preexisting record was seeded in version-3 IndexedDB, then its optional ownership field was stripped to model the legacy shape; after cancellation, it remained, its ID appeared in `legacyProposalIds`, and the API request that had already started was aborted. Three further cases confirmed that cancellation preserves the same proposal after review status, after dismissal, and after deleting/reinserting a new record under the same proposal ID. All callbacks rejected after cancellation.

The record representation adds only an optional private `ownershipToken`; the database version stays 3, with no object store or index changes. Legacy records lacking that field are not treated as writes owned by the cancelling callback. Insertions still use strict-durability IndexedDB transactions. Conditional cleanup requires the captured repository and author key, matching insertion token and exact proposal payload (including operation ID and generation), and no review status or dismissal. The caller receives a token only when its `putProposal` call inserted a new record; ordinary journal callers continue to ignore the return value. `api.propose` accepts an optional client `AbortSignal`; no server route, permission, review, or Core contract changed.

One earlier real-journal attempt did not produce a semantic result because the synthetic operation fixture used an invalid effect value (`propose`). The journal's contract accepts only manuscript, structure, metadata, settings, and migration effects. The failure and full metrics are retained in `/data/scriptorium-core64-worktrees/g4-lifecycle/20261021-c52-c55/playwright-after-fix-real-journal.log` and `after-fix-real-journal.json`; the fixture was corrected to `metadata` for the final run.
