# Core 64 G1 C01/C03/C05 attribution and disposition

This record closes the bounded residual decisions for C01, C03, and C05 on the C02-integrated source. C01 retains the existing W1 reuse, C03 retains complete operation validation, and C05 retains equality-guarded synchronization. No production code change was adopted. The C05 measurements used a temporary opt-in editor probe that was removed after capture; its exact source patch is retained beside this report.

## C01 — text materialization on document changes

`ManuscriptInput` calls `update.state.doc.toString()` once for each `docChanged` update, then passes the same `changedText` to `onChange` and the C02 sentence-index cache. The W1 C01 reuse is already integrated. The existing W1 1 MiB typing p95 values were 641.0/663.1 ms for the two base runs and 599.1/622.9 ms for the C01 runs. Their p50 values overlap base variation, while end-of-input renderer RSS was higher in the C01 runs (6.53/6.65 GiB versus 5.46 GiB). These are historical whole-input measurements, not function-level attribution.

The C05 editor probe recorded 20 `docChanged` materializations for each 20-character typing burst. The 1 MiB burst took 6.8 ms in total, p95 0.4 ms, max 1.4 ms; 100 KiB took 1.4 ms total, p95 0.2 ms; 1 KiB took 0.2 ms total, p95 0.1 ms. Each materialization also supplies the complete text needed by the current callback and sentence-index update. The edit path builds a complete recoverable operation containing the body on each accepted edit. Removing this string alone would require a larger recovery/state boundary change, while the measured cost does not establish enough benefit. Retain W1 reuse and do not reimplement C01.

The C02 cache rebuilds its sentence index on each document-changing update. The whole-page CPU profile is low-sampling and does not separate that index work from editor serialization or operation construction. Do not attribute the large-document typing p95 to C01.

## C03 — operation construction and validation

`SharedApplication.buildOperation` creates the full manuscript write content with `replaceDocumentBody`, assembles read/write preconditions and operation metadata, and calls `assertChangeOperation`. `editText` catches construction/validation failures and records `draftStored: false`. `BrowserJournal.putLatestDraft` validates the complete operation again before opening its strict-durability IndexedDB transaction. The contract validator checks operation identity, generation, repository, effect, bounded path/revision sets, duplicate writes, encoding, and the recoverable-content size limit; it does not scan manuscript contents.

The shared capture completed on source `e8aa3ecd7d1e0bfb3d81a003a2bc0320c9cc6d47`, Chromium `155.0.8059.79`, with 20 typing samples per fixture size. The phase-gated hook wrapped successful `buildOperation` calls including `assertChangeOperation`:

| Fixture | Calls | Total build time | p50 | p95 | Max |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 KiB | 20 | 1.7 ms | 0.0 ms | 0.2 ms | 0.7 ms |
| 100 KiB | 20 | 6.4 ms | 0.3 ms | 0.5 ms | 0.5 ms |
| 1 MiB | 20 | 56.2 ms | 2.3 ms | 3.8 ms | 9.9 ms |

The 1 MiB input phase also included 2 history builds (4.5 ms total), 2 composition builds (4.7 ms), and 1 paste build (2.3 ms). Timings have 0.1 ms resolution and come from one capture. A separate C02 canonical rerun measured 539.0 ms typing p95 at 1 MiB, but the capture is not a causal A/B and does not assign that delay to C03. The hook reports no allocation data and does not measure the later strict journal validation. These measurements do not support relaxing full-operation validation or changing operation construction.

## C05 — controlled-value synchronization

The synchronization effect compares `view.state.doc.toString()` with `value` and dispatches a full-range, no-history replacement only when they differ. Ordinary CodeMirror input calls `onTextChange`, which uses `editText(nextText, true)` and leaves `textRevision` unchanged. Its debounced React publication can update `value` while CodeMirror already contains that text. The effect therefore performs a full-text equality comparison without replacing the document.

The temporary editor probe separately counted those materializations and dispatch bytes during the existing 20-repeat typing, cursor, history, synthetic-composition, paste, and workspace-remount sequence. There were four comparisons during or just after the 20-character typing bursts: one each at 1 KiB and 100 KiB, and two at 1 MiB because the 350 ms publication timer fired mid-burst and again after the last character. The 1 MiB comparisons took 0.3 ms at 10 added characters and 0.2 ms at 20; the smaller documents' single comparisons landed in the cursor phase after the harness advanced. Three paste echoes caused one comparison each, with the 1 MiB case taking 0.3 ms. The entire capture logged 10 comparisons including startup and two between-input transitions, and no full-range dispatch event.

The planned external history-restore count was not checked: the synthetic fixture contains one commit, and its public history request returned HTTP 200 with `snapshots: []`. The panel correctly showed “この原稿の Git 履歴はまだありません。” and exposed no restore action. The browser reported no page errors or alerts. This is `NOT_CHECKED`, not a pass or a synchronization failure. Existing public history-restore behavior is covered by `tests/e2e/core.acceptance.spec.ts`; this C05 probe did not measure that flow's comparison count or dispatch bytes.

A revision gate could theoretically skip the one equality comparison for a same-revision echo, but the measured 1 MiB comparison costs 0.3 ms, no ordinary input caused a replacement, and no external-sync benefit was demonstrated. Do not add revision-gated behavior on this evidence. Retain the equality guard and its external no-history replacement semantics.
