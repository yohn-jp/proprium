# CORE-64 synthetic raw-artifact inventory and archive plan

Prepared against main `b3ba697c9714b34c45c6d9587da5788bf7eb6b33`. This is an inventory and preparation record only: it does not pack or publish an archive, rerun a measurement, or change production code. The inventory is bounded to paths explicitly named by current tracked evidence plus the G0 manifest. No broad `/data` scan or private project data was read.

## Archive contract

Use the existing [performance README](../../scripts/performance/README.md) and [`artifacts.mjs`](../../scripts/performance/artifacts.mjs); do not add another packer or manifest format. The tool's source inventory uses flat, unique `sourceFile` names matching `[A-Za-z0-9][A-Za-z0-9._-]*`, with each corresponding member named `raw/<sourceFile>.gz`. Inventory rows retain source byte count and SHA-256, gzip byte count and SHA-256, and diagnostic/JSONL validity metadata where applicable. Prefix flattened names with the campaign/unit so `browser-small.json` from two campaigns cannot collide.

`pack` consumes an explicit inventory and source directory; it does not discover or classify data. The checked-in G0 `MANIFEST.json`, C21's SHA table, and the derived-workload `SHA256SUMS.txt` are useful source inventories, but none is directly a pack input in the `artifacts.mjs` schema. The C58 manifest is schema 1 with `resultArtifacts`, whereas `pack` expects an `artifacts` array. Build a new archive-specific inventory only after the selected file set is frozen. Keep the raw JSON, traces, profiles, environment/fixture manifests, and named verification logs; keep `summary.json`, `tables.md`, and `c58-summary.json` in Git as derived reports, not raw members.

The existing pack contract is deterministic: gzip level 6, zero mtime, OS byte 255, and sorted ustar with fixed ownership, mode, and timestamps. `pack` requires a new output directory and a permanent HTTPS asset URL; it does not upload. For a campaign bundle, verify the tar with `verify-archive` before extracting, then run `verify` on the extracted root. Preserve failed or superseded captures as explicitly marked diagnostics; do not merge them into primary measurements. The published Wave 0 and Wave 1 releases below remain immutable and are not repacked.

## Finalization sequence

1. Wait for active measurement leases to close. Each owner supplies exact output paths and the matching tracked hash table/manifest; do not substitute a directory glob.
2. Select only synthetic fixture outputs, environment/dataset manifests, profiles/traces, and named verification logs needed to audit a result. Keep `NOT_CHECKED`, failed, and superseded samples as diagnostics with their original names and explanations. Exclude worktrees, pnpm stores, build caches, OCI data, browser state, home directories, unrelated files, and any artifact without synthetic provenance.
3. Stage the explicit list under a new task-specific `/data` source directory. Flatten it with unique campaign-prefixed names and verify each source byte count and SHA-256 against its evidence record. The bounded staging checkpoint is recorded in [the 2026-10-21 partial inventory](results/core64-archive-prep/STAGING-2026-10-21.md) with a schema-compatible hash index; it does not include active or unfinalized campaigns. Create the final archive input inventory only after the selected file set is complete; do not alter existing W0/W1/G0 manifests.
4. Once measurement leases close, the coordinator finalizes the reviewed explicit artifact list and permanent HTTPS asset URL. Then run `pack` to a new output directory, followed by `verify-archive` before extraction and `verify` after extraction. Compare the generated index and archive hashes with the reviewed inventory. This bounded preparation stops before packing or upload; that is a task/resource boundary, not a repository permission requirement. Canonical raw archival remains within the user-authorized campaign scope.
