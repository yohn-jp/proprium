G0 log line 471.

- [`a lost push response is confirmed from the fetched publication ancestor`](../../packages/core/src/transactions.test.ts#L1365): after the remote accepts a checkpoint but kills the push caller, Core returns `confirmed`, acknowledges only the expected operation, and verifies the commit is an ancestor of the published remote head. - [`module disable bounds a non-cooperative action drain and rejects late proposals`](../../packages/module-runtime/src/module-runtime.test.ts#L1328): after disable times out, the resumed action returns `action_cancelled`, the host proposal callback count stays zero, and module status is disabled. The source path complements those cases: [Core validates the proposal snapshot and each operation before journaling](../../packages/core/src/index.ts#L3614), [approval rechecks the observed snapshot and read scopes](../../packages/core/src/index.ts#L3715), and project mutation is serialized by the Core project lock. ## C52 — `VERIFIED_TESTED_HOST_STATE`

The actual `ContributionHost` and contribution catalog passed three Chromium host-state cases with a synthetic trusted Publishing contribution. While disabled, the host showed no selector, called no loader, mounted nothing, and recorded zero fixture timers, held requests, or workers. Enabling and selecting it started one of each; disabling it aborted the signal, disposed the contribution, and returned every active-resource counter to zero. Separate cases verified lazy mount and resource cleanup on direct unmount and scene-snapshot replacement. This verifies these host transitions only. The generated Full loader was replaced by the fixture, so this result does not establish that all Full-profile chunks stay undownloaded or that every installed-disabled module has zero browser activity. The existing G0 test [`disabled modules are not imported; enabling an absent module reports redeployment`](../../packages/module-runtime/src/module-runtime.test.ts#L88) remains separate runtime evidence.

## C55 — `PASS` after the late-callback cleanup fix

The pre-fix real-host deferred-mount case failed as expected: after the old author scope was aborted and the new author scope mounted, resolving the old mount let its delayed `context.propose()` resolve. The fix now checks cancellation before the first journal write, after every awaited journal/API operation, and passes the host abort signal to the client request. A focused Chromium rerun against actual `ContributionHost` and IndexedDB-backed `BrowserJournal` passed all six C55 cases:

1. A callback invoked after author-change abort rejects before writing to the journal or starting a proposal request.
2. A journal write deliberately held until after abort is inserted under the captured old author, conditionally removed, and never sent to the API; the callback rejects and the final record set is empty.
3. An exact preexisting proposal record with the legacy shape (no ownership token) remains in the old author's journal after cancellation; this case starts and aborts the in-flight API request.
4. If the proposal gains an author review status while the API request is held, cancellation leaves the reviewed record intact.
5. If the proposal is dismissed while the API request is held, cancellation leaves the dismissed record intact.
6. If the original ID is removed and reinserted as a newer same-ID record while the request is held, cancellation leaves that newer record intact.

The journal ownership token is a private optional field on proposal records. This change does not increment IndexedDB version 3, add a store or index, or change strict transaction durability. Existing records without a token remain readable and cannot be deleted as if the cancelling call inserted them. `putProposal` now returns an ownership token only for an insertion; the host's cancellation cleanup passes it to `removeProposal`, which also compares the exact proposal payload and preserves any record with a review status or dismissal. The exact payload comparison includes operation IDs and generations. Existing call sites that do not need cleanup ignore the return value. `api.propose` takes an optional client `AbortSignal`; server routes and author approval authority are unchanged.

The direct unmount and scene-snapshot replacement browser cases also passed in this run. These results concern trusted in-process contributions and do not test arbitrary plugin process isolation or a complete permission matrix; those remain `NOT_CHECKED` as stated under C56.
