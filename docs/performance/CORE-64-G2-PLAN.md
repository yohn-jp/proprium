## Existing measurement entrypoints

The synthetic dataset generator supports 10, 1,000, 10,000, and 100,000 tracked files (`small`, `medium`, `large`, `stress`). The existing Core harness supports `read`, `mutation`, `revisions`, `search`, and `stats`; it records elapsed time, Node CPU, RSS/high-water RSS, I/O and Git command counts. It does not currently provide lock contention, `localDurabilityCensus`, repeated `status`, or 10/100-write workloads.

Source review: [CoreStore](../../packages/core/src/index.ts), [Core tests](../../packages/core/src/index.test.ts), [transaction tests](../../packages/core/src/transactions.test.ts), [SnapshotReader and DocumentSource](../../packages/contracts/src/index.ts), [optional Search cache](../../modules/search/src/index-cache.ts), and [Core harness](../../scripts/performance/core.mjs).

After G0 pins the current baseline and its toolchain, the existing command shape is:

```sh
node scripts/performance/dataset.mjs /tmp/c64-g2/large large
node scripts/performance/core.mjs /tmp/c64-g2/large /tmp/c64-g2/revisions-01.json 1 revisions
```

Existing workload invocations are `... 1 read` for cold/warm tree and scene reads, `... 1 mutation` for one-file propose/approve/checkpoint/publish, `... 1 revisions` for one cold/warm revisions pair, `... 1 search`, and `... 1 stats`. Each `revisions` invocation records one cold/warm pair; repeat in five fresh workers with distinct output paths for an n=5 cohort. `search` and `stats` also perform one measured operation per invocation. Use the same fixture, Core profile, worker settings, and command for matching cohorts. The W1 procedure uses `GIT_TRACE2_EVENT` for Git traces. `stress` adds 100 commits as well as 100,000 files; it is not a substitute for an operation-history fixture. Add a bounded synthetic scenario only for a question the current workloads cannot answer.

G0's heavy checks and the goal's required validation were deliberately not run here. Any implementation leaf will use focused Core/contracts regressions, then `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test`, `SCRIPTORIUM_PROFILE=core pnpm build`, and `pnpm audit:core`. C20/C30/cache changes also need the concurrency, boundary, and failure cases specified below; a measurement timeout remains `NOT_CHECKED`.

## Duplicate-contract boundaries

- **C21 / C22 / C35 / C54 — pinned SnapshotReader and bounded object reads.** One reader contract, one path/mode/symlink validation boundary, one batch parser. W1 C22 remains integrated and its cold/warm result remains paired.
- **C30 / C31 / C63 — bounded Git output and retained memory.** Treat these as one memory-bound evidence bundle. A >32 MiB output failure and aggregate cache pressure are distinct observations; do not answer either by a generic buffer increase or cache-cap reduction.
- **C32 / C33 / C36 — derived scans.** Core search, Core statistics, and optional Search keep their current owners. Share only measured immutable work; do not create a parallel framework or make an optional module a Core dependency.
- **C20 / C23 / C27 / C28** all touch writer safety, but their measurement units remain separate: lock wait, temporary-index forks, durability census, and publish replay each have different failure semantics. No shared writer shortcut is authorized.
- **C34** is a local hierarchy grouping question. It may reuse the existing `hierarchySnapshot` file list; it does not justify merging Core search/statistics with the optional index.

## Recommended order and stop rules

1. G0 fixes the post-W1 baseline and verifies which existing measurements still reproduce at the current head. Do not replace the W1 C22 cohort with W0's n=1 observation.
2. Read-only experiments first: C20, C21/C54, C23, C26, C27–C30, C31/C63, C32/C33 and C34. Use the existing harness wherever its workload answers the question; add only the missing synthetic scenarios identified above.
3. Select one smallest implementation leaf only when its own measured benefit and focused correctness proof are available. Keep shared-path ownership on `packages/core/src/index.ts` with one G2 owner, as required by the goal.
4. Mark timeouts and unavailable external probes `NOT_CHECKED`. A full-tree scan, design proposal, cache estimate, or source-level operation count alone is not an observed latency improvement.

No result ledger row is completed by this plan. Record later decisions and measured values in the canonical 64-row results ledger after the relevant G0/G2 evidence exists.
